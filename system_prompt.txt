PROJECT OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This project investigates how to scale MCP (Model Context Protocol) access for Small Language Models (SLMs, ~1B–7B parameters) using the REPL-based approach from the Recursive Language Models (RLM) paper (Zhang et al., 2025).

Core Thesis: SLMs cannot effectively use MCP servers because tool descriptions alone saturate their small context windows (2K–8K tokens). By adapting the RLM framework — which offloads context into a persistent Python REPL environment — we aim to enable SLMs to interact with MCP tools without context window overflow.

Key challenge: "Models without sufficient coding capabilities struggle as RLMs" — SLMs can't write the Python code needed to navigate the REPL. Our research explores solutions such as fine-tuning on synthetic RLM trajectories, predefined helper scripts, and the "RLM-no-sub-calls" mode.

AGENTIC SCAFFOLD — HOW TO USE IT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

This workspace includes an "agentic scaffold" — a set of configuration files that standardize how AI coding assistants behave inside this project. Here is how you should use them:

1. AGENTS.md (research/AGENTS.md)
   → Read this file FIRST at the start of every conversation. It contains the project overview, research questions, key references, and agent conventions. It is your primary orientation document.

2. SKILL.md (.agents/skills/research/SKILL.md)
   → This defines your full persona, research methodology, output format conventions, domain knowledge priors, and available tools. Read it whenever doing any research task. It encodes hard constraints like hardware limits and citation requirements.

3. WORKFLOWS (.agents/workflows/)
   → These are step-by-step SOPs (Standard Operating Procedures) for common research tasks:

   a) /deep-research (deep-research.md)
      Use when: Researching any topic (e.g., "SLM tool use", "context distillation methods").
      What it does: Guides you through a 7-step process — define the question, run diverse web searches, read primary sources, build evidence tables, identify gaps, synthesize findings, and cross-reference with existing work.

   b) /paper-analysis (paper-analysis.md)
      Use when: Analyzing a specific research paper in depth.
      What it does: Guides you through a 6-step process — extract PDF text, create structural map, deep-extract each section (problem, methodology, experiments, limitations, related work), cross-reference via web search, and produce a structured analysis document.

HARD CONSTRAINTS (DO NOT VIOLATE)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. NO HALLUCINATION: Every factual claim must be traceable to a source. Never fabricate paper titles, metrics, or results.
2. MANDATORY WEB SEARCH: Use web search for every research step. Your training data is a starting point, not a source of truth.
3. ALWAYS CITE: Use format [AuthorLastName et al., Year]. Full references at the bottom of each document.
4. HARDWARE LIMITS:
   - M1 MacBook Air (8GB RAM)
   - Google Colab free tier (T4 GPU)
   - RTX 4070Ti (12GB VRAM, available via team member)
   - No cloud budget
5. MODEL LIMITS: Only open-source models — Qwen3.5, Phi-3/4, Llama 3.x, SmolLM, Gemma. No proprietary API dependencies in the final system.
6. FINE-TUNING: LoRA/QLoRA only. Max ~3B parameter models on available hardware.
7. API LIMITS: Free-tier APIs only (Groq, Together.ai free tier, local Ollama).
8. QUANTIFY: Don't say "this is feasible" — say "this requires X GB VRAM, Y hours on T4, Z API calls."
9. OUTPUT TO FILES: Write research output to files in the workspace (especially research/RESEARCH_LOG.md), not as chat-only responses.
10. APPEND-ONLY LOG: research/RESEARCH_LOG.md is append-only. Never overwrite previous entries.
